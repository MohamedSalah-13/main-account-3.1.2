# خطة الانتقال إلى Spring Boot + منصة الإضافات (Plugins)

خطة تنفيذية لثلاثة أهداف مترابطة:

1. جعل Spring Boot هو حاوية التطبيق (DI، معاملات، إعدادات) **مع بقاء JavaFX كواجهة**.
2. إعادة ترتيب الوحدات والملفات بحيث تصبح المزايا الجديدة **إضافات (plugins)** لا تعديلات في النواة.
3. بناء أول إضافتين على هذه المنصة: **الفاتورة الضريبية** و**نظام المناديب**.

**المبدأ الحاكم:** الـ SQL المكتوب يدويًا هو حيث تعيش قواعد العمل — لا يُعاد كتابته.
كل خطوة تنقل الكود دون تغيير منطقه، وتُثبَّت باختبارات قبل الانتقال للتالية.

**قرارات متفق عليها (2026-08-10):**

- الشكل المستهدف: **Spring داخل التطبيق المكتبي (نفس العملية)** — لا فصل خادم/عميل الآن.
  الفصل الشبكي مؤجَّل إلى الملحق (§9)، والخطة مصمّمة كي لا يُهدر شيء لو نُفِّذ لاحقًا.
- الإضافات: **وحدات Maven مدمجة في نفس المستودع**، تُكتشف عبر Spring auto-configuration
  وتُفعَّل/تُعطَّل بمفتاح إعداد أو بالترخيص. لا تحميل jar خارجي وقت التشغيل.
- الفاتورة الضريبية: لم تُحدَّد الجهة بعد. **الافتراض المعتمد:** نبني الضريبة المحلية
  (حساب + طباعة + تقارير) خلف واجهة `TaxAuthorityProvider`، ويُضاف الربط الحكومي
  (ETA المصرية أو ZATCA السعودية) لاحقًا كإضافة فرعية دون لمس النواة — §7.4.
  **راجع §7.4 قبل بدء المرحلة ج** لأن تحديد الجهة يغيّر حجم العمل هناك وحده.

## 1. حالة المشروع اليوم

### الحجم (محسوب في 2026-08-10)

| المقياس | القيمة |
|---|---|
| ملفات Java (`account` + `controlsfx`) | 588 |
| ملفات FXML | 63 |
| DAOs | 53 |
| Services | 40 (كلها `record X(DaoFactory)`) |
| مواضع `insertMultiData` (حدود معاملات) | 18 |
| ملفات تستخدم `DaoFactory` خارج `service/` و`model/dao/` | 78 |
| نداءات `ServiceRegistry.get(...)` | 95 |
| موديلات domain تستخدم JavaFX `Property` | 28 |
| اختبارات | 4 أصناف فقط |

### ما تم إنجازه بالفعل (تغيّر عن نسخة الخطة السابقة)

- ✅ **Flyway مُفعَّل ويعمل.** `V1__baseline.sql` + `V2__audit_triggers.sql` +
  `V3__item_barcodes.sql`، يشغّلها `DatabaseMigrationService` من constructor الـ
  `DownLoadApplication`. الخطوة «استبدال نظام الترقية بـ Flyway» **مكتملة** — لا تُعَد.
- ✅ إعداد قاعدة البيانات مشفَّر ومعزول (`CryptoDatabaseConfig`, AES/GCM, `v2:`).
- ✅ نظام إشعارات كامل بنقطة امتداد جاهزة (`NotificationSource`) — أقرب شيء في
  المشروع لعقد إضافة، وسنبني عليه.
- ✅ `ConnectionManager` يربط الاتصال بالـ thread — وهو **نفس نموذج Spring
  `@Transactional` بالضبط**، فالتحويل تعديل في ملف واحد.

### العوائق (مرتبة حسب الخطورة)

**ع-1 — لا توجد شبكة أمان اختبارية.** 4 أصناف اختبار فقط، ولا شيء يغطي الـ DAOs ولا
حدود المعاملات الـ 18. أي نقل بلا اختبارات = كسر لا يُكتشف إلا عند العميل.

**ع-2 — `ServiceRegistry` service locator ثابت.** 95 نقطة استدعاء، و38 سطر تسجيل يدوي
في `DownLoadApplication`. يعيد `null` بصمت لو تغيّر ترتيب التسجيل. هذا بالضبط ما يمنع
أي إضافة من تسجيل خدماتها.

**ع-3 — 78 ملفًا يتجاوز طبقة الـ services ويمسك `DaoFactory` مباشرة.**
لا يوجد حد API واضح تُبنى عليه الإضافات.

**ع-4 — النواة مغلقة أمام الامتداد.** الأزرار في `MainToolbarController` ثابتة في FXML،
وقواعد الإشعارات قائمة صريحة في `NotificationBootstrap.sources()`، والصلاحيات `enum`
مغلق (`UserPermissionType`). لا يمكن لإضافة أن تضيف شاشة أو زرًّا أو صلاحية.

**ع-5 — `TrialManager` مستدعى من داخل الـ DAOs** (`ItemsDao`, `CustomerDao`,
`TotalsBuyDao`, `TotalsSalesDao`) و`MAX_FAILS = 1` — أي false positive يقفل النسخة
نهائيًا. **لا تُضف أي مسار فشل جديد هنا، ولا تجعل الإضافات تمرّ به.**

**ع-6 — 28 موديل domain يستخدم JavaFX `Property`.** يمنع أي تسلسل (JSON/XML) — وهو
ما تحتاجه الفاتورة الضريبية تحديدًا عند الربط الحكومي.

**ع-7 — بناء تراكمي يتخطى التعديلات صامتًا** ومئات أخطاء Lombok الوهمية من خطأ واحد
(موثَّق في `CLAUDE.md`). ينعكس على بوابات التحقق في هذه الخطة.

## 2. قواعد «ألا نفقد المشروع»

هذه ليست نصائح عامة — كل واحدة تقابل عائقًا أعلاه، وتُطبَّق حرفيًا في كل خطوة.

| # | القاعدة | لماذا |
|---|---|---|
| ق-1 | **`main` تبقى قابلة للشحن دائمًا.** كل خطوة على فرع خاص، تُدمج فقط بعد بوابة التحقق. | لا يوجد فرع «إعادة كتابة» يعيش شهورًا ثم لا يُدمج أبدًا. |
| ق-2 | **لا خطوة كبيرة.** أي خطوة لا يمكن مراجعتها في جلسة واحدة تُقسَّم. | ع-1: بلا اختبارات، المراجعة اليدوية هي شبكة الأمان الوحيدة. |
| ق-3 | **الاختبارات قبل النقل، لا بعده.** لا يبدأ نقل مسار كتابة قبل وجود اختبار يصف سلوكه الحالي. | ع-1 |
| ق-4 | **`mvn clean` دائمًا عند التحقق**، و`-am` مع `-pl account`. | ع-7 |
| ق-5 | **التوافق للخلف إلزامي.** الطبقة القديمة تبقى تعمل كغلاف رفيع فوق الجديدة حتى تفرغ نقاط الاستدعاء. | ع-2: 95 نقطة لا تتغير دفعة واحدة. |
| ق-6 | **الهجرات إلى الأمام فقط.** لا تُعدَّل هجرة شُحنت، ولا يُعاد طيّ شيء في `V1`. | عميل شغّلها فعلًا لن يشغّلها ثانية. |
| ق-7 | **الإضافة لا تعدّل جداول النواة.** تملك جداولها وتربطها بمفتاح الفاتورة/الصنف. | يجعل تعطيل الإضافة عملية آمنة، ويمنع تضخّم `V1`. |
| ق-8 | **كل إضافة خلف مفتاح تعطيل**، وتعطيلها يعيد سلوك ما قبلها بالضبط. | خطة تراجع فورية لا تحتاج نشر إصدار. |
| ق-9 | **`TrialManager` منطقة محظورة.** لا مسارات فشل جديدة، ولا فحوص ترخيص للإضافات داخله. | ع-5: `MAX_FAILS = 1`. |
| ق-10 | **نسخة قاعدة بيانات قبل كل ترقية عند عميل حقيقي.** `DatabaseMigrationService` يشغّل `mysqldump` تلقائيًا — تأكّد أنه يعمل قبل أي شحنة تحمل هجرة. | ق-6 لا تكفي وحدها. |

**بوابة التحقق بعد كل خطوة (تُشغَّل كما هي):**

```bash
mvn clean test
```

يليها تشغيل التطبيق فعليًا مقابل قاعدة بيانات — `mvn clean test` وحده لا يثبت شيئًا
في هذا المشروع، فالتغطية شبه معدومة.

## 3. البنية المستهدفة

### الوحدات

```
main (pom)
├── controlsfx                     مكتبة الواجهة المشتركة  (موجودة)
├── platform                       عقد الإضافات + الأحداث + DTOs   (جديدة)
├── account                        النواة: الشاشات والخدمات والـ DAOs  (موجودة)
├── plugins/
│   ├── plugin-tax-invoice         الفاتورة الضريبية   (جديدة)
│   └── plugin-sales-reps          نظام المناديب      (جديدة)
└── app                            التجميع: Main + shaded jar   (جديدة)
```

**اتجاه الاعتماد (لا دورات):**

```
platform  ◄── controlsfx
    ▲            ▲
    │            │
 account ────────┘
    ▲
    │
 plugins/*        app ──► account + platform + plugins/*
```

`account` **لا يعتمد على أي إضافة**. الإضافات تعتمد على `account` لتستخدم خدماته،
و`app` هي الوحدة الوحيدة التي تعرف الاثنين معًا وتنتج الـ jar النهائي. هذا ما يجعل
إضافة/إزالة إضافة تغييرًا في `app/pom.xml` فقط.

> **ملاحظة على `platform`:** غرضها الوحيد هو كسر الدورة — عقود يعرفها الطرفان.
> لا تضع فيها منطق عمل، ولا تجعلها تعتمد على JavaFX (لتبقى صالحة للخادم لاحقًا، §9).

### عقد الإضافة

```java
// platform: com.hamza.platform.plugin
public interface AccountPlugin {
    String id();                                  // "tax-invoice"
    String displayName();                         // "الفاتورة الضريبية"
    default List<MenuContribution> menu()         { return List.of(); }
    default List<PermissionContribution> perms()  { return List.of(); }
    default Optional<String> migrationLocation()  { return Optional.empty(); }
    default Optional<String> messagesBundle()     { return Optional.empty(); }
}
```

الخدمات وقواعد الإشعارات و«خطّافات» الفاتورة **لا تُذكر في العقد** — تُعرَّف كـ Spring
beans في auto-configuration الإضافة، وتلتقطها النواة بالنوع. العقد للأشياء التي لا
يكفي فيها النوع وحده.

### نقاط الامتداد الستّ

| # | نقطة الامتداد | كيف | تعمل بعد الخطوة |
|---|---|---|---|
| ن-1 | **خدمات ومستودعات** | `@Bean` في auto-configuration الإضافة | 2 |
| ن-2 | **هجرات قاعدة بيانات** | موقع Flyway خاص + جدول history خاص بالإضافة | 5 |
| ن-3 | **قائمة/أزرار/شاشات** | `MenuContribution` + `@FxmlPath` كما هو | 6 |
| ن-4 | **قواعد إشعارات** | `@Bean NotificationSource` تلتقطه النواة | 6 |
| ن-5 | **خطّافات الفاتورة** | `InvoiceExtension` (قبل/بعد الحفظ + احتساب الإجماليات) | 6 |
| ن-6 | **صلاحيات وترجمات** | `PermissionContribution` + bundle إضافي | 6 |

**ن-2 مهمة بشكل خاص:** كل إضافة تحصل على `locations = db/migration/<plugin-id>`
و`table = flyway_history_<plugin-id>` منفصل. بهذا لا تتصادم أرقام `V1` الخاصة بالإضافة
مع `V4` القادمة في النواة، ويمكن تركيب إضافة على تثبيت قائم دون لمس تاريخ هجرات النواة.

**ن-5 هي أصعبها ولها قسم خاص** — §6.3 — لأن الفاتورة الضريبية والمناديب كلتاهما تعلّقان
عليها، و`BuyController2` هو نقطة التعليق الحالية.

## 4. المرحلة أ — أساس Spring (بلا شبكة، بلا إضافات)

الهدف: DI حقيقي، `@Transactional` صريحة، واختبارات تعمل. **لا شيء هنا يغيّر سلوكًا
مرئيًا للمستخدم** — هذا هو المقياس.

### الخطوة 0 — شبكة الأمان الاختبارية *(إلزامية أولًا — ق-3)*

لا تبدأ الخطوة 1 قبل اكتمالها.

- [ ] **0.3** اختبار توصيفي لكل حد معاملة من الـ 18، يتحقق من **صفوف قاعدة البيانات**

### الخطوة 1 — وحدة `platform` وSpring context

- [ ] **1.1** إنشاء وحدة `platform` (Java عادي، بلا JavaFX وبلا Spring في البداية).
- [ ] **1.2** إضافة `spring-boot-starter` + `spring-boot-starter-jdbc` للـ `account`

- [ ] **1.3** `AppConfig` بـ `@Configuration`: يعرّف `DataSource` بنفس إعدادات Hikari

- [ ] **1.4** قراءة `config.xml` المشفَّر تُغذّي `spring.datasource.*` عبر

- [ ] **1.5** `Flyway` يُدار كـ bean بدل `DatabaseMigrationService` المباشر —
      **مع الإبقاء على الثلاثة أشياء التي يضيفها حول Flyway** (إنشاء القاعدة إن لم توجد،
      رفض baseline لقاعدة أجنبية، `mysqldump` قبل الترقية). هذه ليست تفاصيل: كل واحدة
      منها عالجت مشكلة حقيقية. انقل المنطق، لا تستبدله بـ `spring.flyway.*` وحده.
- [ ] **1.6** التحقق: التطبيق يفتح ويعمل. اختبارات الخطوة 0 تمر.

### الخطوة 2 — استبدال `ServiceRegistry` بـ DI

- [ ] **2.1** تحويل الـ 40 service إلى `@Service` — تبقى `record`، وSpring يحقن عبر
      الـ constructor.
- [ ] **2.2** `DaoFactory` يصبح `@Bean`.
- [ ] **2.3** **`ServiceRegistry` يبقى بنفس توقيعه** لكن `get()` يفوّض إلى
      `ApplicationContext` (ق-5). الـ 95 نقطة استدعاء **لا تتغير في هذه الخطوة**.
- [ ] **2.4** حذف الـ 38 سطر تسجيل يدوي من `DownLoadApplication`.
- [ ] **2.5** `OpenFxmlApplication` يبني الـ controllers عبر الـ context
      (`setControllerFactory`) — بهذا تصبح الـ controllers قابلة للحقن، **وهو الشرط
      الذي بدونه لا تستطيع أي إضافة أن تقدّم شاشة**.
- [ ] **2.6** تفريغ نقاط `ServiceRegistry.get` تدريجيًا لصالح الحقن، على دفعات حسب
      المجلد. غير عاجل، ولا يوقف المراحل التالية.

**ما لا يتغير:** أي FXML، أي DAO، أي استعلام.

### الخطوة 3 — نقل المعاملات إلى Spring *(أهم خطوة تقنية في الخطة)*

- [ ] **3.1** تعديل `ConnectionManager.acquire/release` لاستخدام

- [ ] **3.2** تشغيل اختبارات 0.3–0.6 بلا تعديل. **لو فشلت، توقّف** — سلوك المعاملة تغيّر.

- [ ] **3.4** حذف `beginTransaction`/`endTransaction`/`inTransaction` بعد خلوّ الكود منها.
- [ ] **3.5** تحديث `CLAUDE.md` بحدود المعاملات الجديدة — الملف يصف اليوم النموذج القديم.

**معيار الاكتمال:** كل حد معاملة صريح ومعلَن، ولا شيء يعتمد على `ThreadLocal` مخصص.

## 9. ملحق — الفصل الشبكي (مؤجَّل)

القرار الحالي: **لا فصل خادم/عميل**. هذا الملحق يوثّق ما تحفظه الخطة الحالية لصالح ذلك
اليوم، وما سيبقى ناقصًا:

**جاهز مسبقًا بعد المرحلة أ:** `@Transactional` صريحة (تصبح حدود endpoints مباشرة)،
Spring context، `platform` بلا JavaFX، Flyway لكل وحدة.

**الناقص وقتها:** DTOs بدل الـ 28 موديل JavaFX (ع-6)، إغلاق الـ 78 ملفًا التي تتجاوز
الـ services (ع-3)، endpoints خشنة (**واحد لكل عملية عمل مكتملة، لا لكل DAO** — وإلا
انكسرت ذرّية الفاتورة)، فلترة وترقيم في SQL بدل Java، تعدد مستأجرين
(**قاعدة لكل مستأجر عبر `AbstractRoutingDataSource`** — عمود `tenant_id` يعني مراجعة
كل استعلام يدويًا ومخاطرة تسريب بين العملاء؛ لا تسلكه)، ونقل `TrialManager` و`BackupService`
و`Preferences` إلى الخادم.
